# 历史升级机制（网页版）

## 问题从哪来

网页版把「回放页 HTML」整个存在**用户浏览器的 IndexedDB** 里 —— 那是生成那一刻的
成品，没法重新生成（重跑要完整的 Pyodide + 原图，而历史记录里只有成品和 SVG）。
可回放页的布局 / 交互 / 时间轴一直在改：用户上周存的作品，打开时还是上周的样子。

所以：**打开 / 下载历史作品时，把老页面「升级」成新样子**。升级只在内存里做，
**不动 IndexedDB 里的原件**（升级逻辑出 bug 也不会弄坏存档）。

这套升级逻辑全部在 **`web/upgrade.js`**（纯函数库，不碰 DOM / Blob / IndexedDB，
所以能在 Node 里直接测）；`web/index.html` 只负责 IO：读 Blob 文本 → 调库 → 包回
Blob，并按记录 id 缓存结果。

## 两个时代

### ① 无版本戳时代（2026-09-14 之前的产物）：模糊规则

老页面里没有任何版本信息，只能靠**文本指纹猜它生于哪一代** ——
`LAYOUT_RULES`（42 条文本替换 / 正则）+ `AXIS_OLD/NEW`（时间轴整段替换）。
这条路线修过两个结构性事故，代价和细节见 [踩坑记录 #18 / #19](踩坑记录.md)：

- 规则只能累积（要兼容更老的），越滚越大；
- 「这条打过了吗」只能靠启发式判定（幂等断言兜底）。

**42 条规则现在是「冰冻遗产」**：只为无戳存量服务，不再新增。新改动一律走下面的迁移链。

### ② 版本戳时代（v1 起）：精确迁移链

生成端（`tools/svg2canvas.py` 的 TEMPLATE）在页面 `<title>` 前埋一行：

```html
<!-- p2sv-gen: v1 -->
```

升级端读到版本号后：

- **有戳** → 走 `MIGRATIONS` 精确迁移链：从 vN 逐级找 `{ from: N, to: N+1, apply }`，
  应用一条、版本号推进一级，直到 `GEN_LATEST`；
- **无戳** → 先跑 42 条模糊规则（能升多少升多少），补戳为 **`LEGACY_TARGET`（=1，
  模糊规则的等价版本，恒不变）**，然后同样接上迁移链。

迁移的约定：

- `apply(text)` 返回**升级后的文本**，或返回 **`null` 表示「这段代码不在这份产物里」**
  —— 跳过，但版本号照常推进（不推进会卡死；缺环才停下并记 note）；
- 迁移抛异常 → 捕获、记 note、照样推进；
- **幂等性由版本号保证**：迁移完成版本号已变，再跑一遍对不上 from，天然不会重复。
  ——「这条打过了吗」的启发式判定从此不需要了。

## 日常操作：改回放页模板时做什么

改了 `tools/svg2canvas.py` 的 `TEMPLATE`（布局 / 脚本 / 行为）时，固定三步：

1. **打戳**：把模板里 `<!-- p2sv-gen: vN -->` 的 N 加一；
2. **登记迁移**：`web/upgrade.js` 里 `GEN_LATEST` 加一，并给 `MIGRATIONS` 追加一条
   `{ from: 旧版, to: 新版本, apply }` —— 把「新老代码对照」写进 apply（就像当年
   写 LAYOUT_RULES 那样，但这次只写一条、只关心相邻两版、写完就冻结）；
3. **跑测试**：

   ```bash
   node tools/test_upgrade.js        # 逻辑断言（93 项：版本戳 / 幂等 / 防重复 / 迁移链）
   python3 tools/test_upgrade.py     # 再加浏览器级验证（需 playwright）
   ```

   `python3 tools/smoke_test.py` 也会跑逻辑断言那步（node 在时）。

**只想改生成端、不管历史？** 不可以跳第三步 —— 迁移的期望值写在测试里，
`FEATURES` 表（`tools/test_upgrade.js`）按样本世代声明「升级后应拿到什么」，改了模板
就该按需更新它，让测试继续钉住行为。

## 黄金样本测试（tools/test_upgrade.js）

`tests/fixtures/*.html` 是六个世代的**真实回放页产物**，从 git 历史里「复活」：
逐个 checkout 当年的 `tools/svg2canvas.py`、用同一张小图 + 小 SVG 重新跑出来
（`tools/make_upgrade_fixtures.py`，管线确定性的，重生成结果字节级一致）。

| 样本 | 来源 | 世代特征 |
|---|---|---|
| s1 | `29770ea` | 初版：金色 UI、老时间轴、无缩放 |
| s2 | `f742973` | 加缩放与平移 |
| s3 | `0f648ca` | 相册式缩放（√面积时间轴） |
| s4 | `eaa6ea5` | 双栏各自独立 |
| s5 | `9ab8b88` | 图片描述版（现状前一版） |
| s6 | 工作区 | 当前模板（带 v1 戳）——用来验证「有戳产物零改动直通」 |

断言五类：**版本戳**（升级后 = GEN_LATEST 且只有一个戳）、**幂等**（升级结果去戳
再升 = 从原件升，杜绝重复插入）、**防重复哨兵**（`var fitW` / `#fsExit` /
`id="view"` 计数与最新模板一致）、**逐样本特性**（老世代该拿到的升级都拿到）、
**迁移链机制**（多级链 / 未命中推进 / 缺环停止 / 异常兜底，用假迁移单测）。

## 已知边界

- **s1（最老世代）升级后没有完整的缩放交互**：那代页面里根本没有缩放系统，
  文本替换补不出整套函数。结果页面能播能看、零报错（「安全降级」）——这是
  42 条规则的设计边界；且网页版 9-12 才上线，用户历史里不可能有这代产物，
  s1 只用于压测最坏情况。测试对它断言「结构升级 + 不破坏」，不断言全套交互。
- **存量（无戳）产物每次打开都会重跑一遍模糊规则**（不写回原件）——规则命中后
  `alreadyApplied` 会快速跳过，毫秒级，可接受。
- **`classic.html`（经典版）不参与新链**：它保留自己内置的那套旧升级逻辑
  （与新版分叉自同一份代码），定位就是「老版原样保留」；新版页面继续演进时，
  classic 不跟。
- **mock 模式生成的回放页**（无 worker.js 时的内置演示器）也埋最新版戳 ——
  跳过模糊规则、免被误伤。

## 相关文件

| 文件 | 角色 |
|---|---|
| `web/upgrade.js` | 升级库（版本戳 / 迁移链 / 冻结的模糊规则 / 总入口 `upgradeReplay`） |
| `web/index.html` | 调用方（IO + 缓存），`const UP = window.P2SVUpgrade` |
| `tools/svg2canvas.py` | 生成端：模板里打戳（改模板时同步加一） |
| `tools/test_upgrade.js` | 逻辑断言（node） |
| `tools/test_upgrade.py` | 逻辑断言 + 浏览器验证（playwright 可选） |
| `tools/make_upgrade_fixtures.py` | 从 git 历史重造黄金样本 |
| `tests/fixtures/` | 六个世代的样本 + 说明 |
