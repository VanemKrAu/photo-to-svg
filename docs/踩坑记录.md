按「被发现 → 定位 → 修法」的顺序记。**每条都真实发生过，改代码前先读这里。**

## 1. `--order sketch` 的「线稿」根本不是线稿

**现象**：用户看回放说「这画得乱七八糟的，还不是先画的线稿」。

**定位**：`build_svg_art.py` 的 `order_shapes()` 里，所谓线稿的筛选条件是

```python
thin_cap = max(24.0, total_px * 0.0002)      # ≈622 px²
if area > thin_cap: continue                 # 只筛「面积够小」
if perimeter / (2*sqrt(pi*area)) >= 2.0: ...  # 只筛「形状够细长」
head = lines[: int(len(shapes) * 0.02)]      # 再按周长降序取前 2%
```

实测被选中的前 2163 笔：**bbox 中位数 31×21**，bbox 覆盖率 **61.9%**。
也就是说它们是**全图颜色过渡处的细长碎片**（天空色带、海浪纹、沙滩颗粒），
散布在整幅画面上，跟人类画线稿（沿物体轮廓、首尾相连）完全不是一回事。

**修法**：不要指望 `--order` 给线稿。真正的线稿层由 `svg2canvas.py` 的
`build_lineart()` 从原图单独提取（见 #5），插在所有色块最前面。

## 2. 纯 SVG 版有「白点」

**现象**：用户反馈「svg 图片里面有白色的部分好像是没画到一样，零零散散的白点」。

**定位**：`write_svg()` 写出的 `<path>` **只有 fill、没有 stroke**，而 `write_html()` 写出的
自带 `stroke="{同fill}"` + CSS `stroke-width`。色块是互不重叠的平面划分，轮廓简化
（epsilon）会让相邻色块之间留下发丝级细缝；HTML 版靠同色描边把缝糊住，纯 SVG 版没有描边
→ 缝里露出底层 `<rect fill="#f0f0f0">` 的浅灰底，在深色区域就是刺眼的白点。

**修法**（`make_art.py` 已自动做）：

```python
t = re.sub(r'<path fill="([^"]+)" fill-rule="evenodd"',
           r'<path fill="\1" stroke="\1" fill-rule="evenodd"', t)
t = t.replace('</title>', '</title>\n<style>path{stroke-width:0.6;stroke-linejoin:round}</style>')
```

1440×2162 原生分辨率实测：亮斑 7091 → 379 个（−95%），MAE 4.93 → 4.04。

## 3. stroke-width 越大越糊

**现象**：修完白点后用户说「这样感觉非常糊，能不能更清晰一点」。

**定位**：同色描边会把每个色块**向外撑 stroke/2**。图里有 4.8 万个只有 2~4px 的小色块，
被撑大之后直接被隔壁颜色吃掉，细节就没了。

1440 原生分辨率实测（对照原图算 SSIM）：

| 配置 | SSIM@1440 | MAE | 白点 |
|---|---|---|---|
| 顶配 67990 笔 + **sw 1.8** | **0.8642** | 4.39 | 1076 |
| 顶配 67990 笔 + 无 stroke | 0.8864 | 3.85 | 14578 |
| 顶配 67990 笔 + sw 0.6 | 0.9126 | 3.49 | 812 |
| 超高精度 182640 笔 无 stroke | **0.9434** | 2.24 | 687 |

**结论**：① 描边最优区间 **0.3~0.6**，1.8 反而最糊；② **想更清晰，加形状数远比加描边有效**；
③ 算 SSIM 缩放必须统一用 `cv2.INTER_AREA`，用 LANCZOS 会得出相反结论。

## 4. 「线稿画着画着突然大面积上色」

**现象**：用户反馈线稿阶段结束后画面「啪」地糊上一大片。

**两个原因叠加**：

1. 速度曲线突变——原来线稿阶段每笔耗时是后面的 27 倍，过点后速度猛提。
2. **笔的粒度断崖**（主因）——色块按面积降序排，实测

   > **整幅画面 75% 的面积，是在前 1.94% 的笔里铺完的。**

   线稿 2621 笔之后，紧接着的第 88 笔就盖掉了半个画面。

**修法**：

- **时间权重 = `0.15 + bbox面积 × 0.002`**（大色块慢慢铺、小碎片快过）。
  线稿笔的权重由「线稿时间占比」反解，保证起稿阶段占满指定比例。
  面积数组作为 `Uint32×N` 追加在 payload 末尾，JS 用累计权重表 + 二分查找做
  「时间 ↔ 笔序号」双向映射。**别用分段线性曲线**。
- **大色块扫描线切分**：bbox 面积 > 7000 的色块，用 `cv2.fillPoly` 光栅化后按横条切开
  （step = 9000/宽度，夹在 [8, h]），像大笔刷一横条一横条刷上去。

改后覆盖曲线（90 秒 / 15% 线稿）：

| 时间 | 15%(线稿毕) | 25% | 35% | 45% | 55% |
|---|---|---|---|---|---|
| 画面已铺 | 11% | 32% | 60% | 87% | 96% |

## 5. 线稿做成了「几何色块」

**现象**：用户看走廊人像的回放，说「你这也不是线稿啊全是几何形状」。

**定位**：`build_lineart()` 一开始用的是

```
Canny → dilate 膨胀 → findContours 取外轮廓 → 用多边形 fill
```

边缘一到密集区域（棕榈叶、百叶窗、木纹、栏杆立柱），膨胀后会连成一整片，
轮廓简化成一个多边形，**一填充就是一坨灰色三角形**。

**修法**：不再膨胀、不再填充。改成「**折线追踪 + 描边**」：

1. Canny 得到 1px 边缘，把边缘像素放进 `set`
2. 按 8 邻域走链，优先从度=1 的端点起步（保证一条线尽量完整），剩下的闭环再任意起头
3. `approxPolyDP(1.0, closed=False)` 简化，按 `seg_pts=16` 点切段
4. **用 `ctx.stroke()` 画**（`lineCap/lineJoin=round`，线宽默认 2.6 画布像素）

类型标记：颜色值的 `0x02000000` 位表示「这一笔是描边，不填充」。

**效果对比**（走廊人像 1440×2012）：

| | 填充式（错） | 折线描边式 |
|---|---|---|
| 线稿落在真实边缘上 | 64.7% | **97.8%** |
| 墨水占画面 | 11.18% | 6.52% |

## 6. 线稿整体错位 / 看着像「另一张图的线稿」

**现象**：用户说「你最开始给我弄那个线稿图，预览是上一次海边人像的那个线稿图」。

**定位**：`svg2canvas.py` 里把画布尺寸**硬编码成了 1440×2162**（海边那张的尺寸）。
但走廊人像是 **1440×2012**。于是：

```
原图 1440×2012 → 被拉伸成 1440×2162（高 7.5%）→ Canny 提边缘（坐标是 2162 高的）
             → 画到 1440×2012 的画布上 → 超出部分被裁掉
```

两头都错：线条纵向滑位（越靠底部错得越多，底部差 150px），底部还有一整段被裁。
同时页面里 `<canvas height="2162">` 也和实际画面不符，显示时被再拉一次。

**修法**：画布尺寸**一律从 SVG 的 `viewBox` 读**：

```python
mv = re.search(r'viewBox="0 0 ([\d.]+) ([\d.]+)"', head)
CW, CH = int(float(mv.group(1))), int(float(mv.group(2)))
```

修完「线稿落在真实边缘上」21.6% → 64.7%（后经 #5 再提到 97.8%）。
`make_art.py` 已加「SVG viewBox / 页面 canvas」三方尺寸自检，不一致直接报错退出。

> 自检本身也要**流式扫描**：回放页 `--ghostimg` 的原图 base64 有两三百 KB，
> `read(N)` 读不到后面的 `<canvas>`。

## 7. 出现很多横向白线

**现象**：用户说「出现了很多白线，上一次还没有」。

**定位**：新加的扫描线切分（#4）里，相邻横条的像素范围不重叠：

```
条0 覆盖到第 134 行
条1 从    第 135 行开始     ← 中间缺一行，露出底色 #f0f0f0
```

**修法**：让每条多含一行 —— `mask[yy : yy+step+1]`，相邻条共享同一行像素。

修复后逐行扫描（找「近白像素占比突然飙升」的行）：成片 → **只剩 3 行**
（其中 2 行在地平线位置，那里原图本身就是亮的）。

## 8. 手机打开非常卡

**现象**：用户说「我现在手机已经非常卡了，这个十几兆的 HTML 文件我打开就很卡了，不能优化一下吗？两者必须取舍是吧？」

**定位**：`write_html()` 把 N 个 `<path>` **全部塞进 DOM**，每个还挂一条 CSS 动画。
67990 笔时手机就卡，18 万笔根本打不开。

**修法**：改用 Canvas（`svg2canvas.py`）：

- DOM 里只剩 **1 个 `<canvas>`**，笔数据打包成二进制 base64 内嵌
- **逐帧增量绘制**（只画新增的几十笔），拖动回退时才整幅重画
- 拖动节流到 `requestAnimationFrame`
- 解码用 `new Uint8Array(L)` + for 循环，**别用 `Uint8Array.from(atob(s), …)`**
  （12 MB 会生成 900 万元素的中间数组）

| | 旧 HTML | 新 Canvas |
|---|---|---|
| 笔数 | 67990 | **182640** |
| 文件 | 20.9 MB | **12.4 MB** |
| DOM | 67990 path + 67990 动画 | **1 canvas** |
| SSIM@1440 | 0.9126 | **0.9406** |

**所以「清晰」和「流畅」不必取舍——瓶颈是渲染方式，不是数据量。**

## 9. 解析 path 的正则被属性顺序坑了

**现象**：`make_art.py` 首次端到端自检时，`svg2canvas.py` 解析出 **0 个色块**。

**定位**：`make_art.py` 的「补描边」步骤会在 `fill` 和 `fill-rule` 之间插入 `stroke`，
而 `svg2canvas.py` 的正则写死了属性顺序：

```python
re.compile(r'fill="([^"]+)" fill-rule="evenodd" d="([^"]*)"')   # ✗ 匹配不到
```

**修法**：放宽成不依赖顺序：

```python
re.compile(r'fill="([^"]+)"[^>]*?d="([^"]*)"')                   # ✓
```

## 10. 命令行参数错位

**现象**：生成出来的线宽是 `0.25`（本意是 2.6），线细到看不见。

**定位**：`svg2canvas.py` 的位置参数是

```
<in.svg> <原图> <out.html> <标题> <秒数> <线稿笔占比(0=自动)> <线稿时间占比> [线稿线宽]
```

调用时把 `epsilon` 传到了第 8 位（线宽的位置）。

**教训**：参数一多就容易错位。`make_art.py` 是唯一入口，它的参数顺序固定为
`<原图> <作品名> [标题] [秒数] [线稿时间占比] [epsilon] [线宽]`，改调用时**数一遍位数**。

## 11. 越还原越好，但 epsilon 可以「白捡」

**现象**：需要在「保真」和「体积」之间取舍。

**定位**：`epsilon` 是轮廓简化容差，它**只影响顶点数，不影响形状数**：

```
epsilon 0.08 → 形状 182640，顶点 2951257，SSIM 0.9434
epsilon 0.25 → 形状 182640，顶点 1490435，SSIM 0.9406      ← 顶点少一半，SSIM 只差 0.003
```

**结论**：给 Canvas 回放页（要发到手机上）时用 0.25，文件从 20.5 MB 降到 12.4 MB；
要极致保真的矢量原图时用 0.08。

## 12. 其它零碎

- **`--background` 默认是 `#000006`（近黑）**，明亮图必须显式给原图高频色。
  源码里「与底色色差 ≤3 的量化色」会**整簇跳过不画**，底色选错会让一片区域直接消失。
- **暗背景图**加 `--dark-cut 14`，否则暗部会被整簇压平。
- **`--base`** 按 `60 ÷ 笔数` 估算，让 1× 播放落在 60 秒左右；忘了给会变成几十分钟。
- **千万不要用「读图片」工具读 png/jpg**，改用 Python 分析像素（见 AGENTS.md 规则 1）。
- **不要往工作区根目录扔文件**——用户为此发过火，产物一律进 `output/<作品名>/`。
- **不要生成用户没要求的文件**。曾自作主张放了一张「线稿层预览.png」，
  用户说「你怎么也给我弄了个线稿图预览，而且预览图还不对」。

## 13. 底色选错 → 满图白点

**现象**：网页版生成的一张海边照，画面边缘和阴影处出现成片白点。
用户对比原图后指出「为什么又出现白点了」。

**定位**：`pick_background()` 在最高频色占比 ≥5% 时就拿它当底色，
而底色的作用是「哪些颜色可以整簇跳过不画」（源码里 `|rgb - matte| ≤ 3` 就跳过）。
那张照片的最高频色是 `#686868`，占 **5.94%**，刚好越过阈值 ——
而 `#686868` 正是画面里的**阴影灰**。于是人物和沙滩上的阴影被整簇挖掉，
底下 `#f0f0f0` 的底板从缺口透出来，就是白点。

**修法**：阈值从 5% 提到 **12%**，且只在明确是「统一背景」时才用高频色；
其余一律用画面里不存在的中性色（`#f0f0f0` / `#101010`，按画面明暗挑）。

| | 旧阈值 5% | 新阈值 12% |
|---|---|---|
| 那张海边照 | 误用 `#686868` → 挖空阴影 | 用 `#f0f0f0` → 安全 |
| 色块数 | 52,467 | **52,988**（多画出 521 块被挖掉的内容） |
| 孤立亮点 | 成片 | **0.0001%** |

代价是底色与画面不同时，SVG 体积略增（底板色差大时压缩率差一点），
但换来「绝不会挖空画面」——这笔账很划算。

**排查提示**：如果以后再见到白点，先看 `pick_background` 选了什么色，
再用 `|rgb - matte| ≤ 3` 去原图里数一遍有多少像素会被跳过。

## 14. 回放页工具栏在窄屏溢出，倍速按钮点不到

**现象**：手机上打开回放页，底部工具栏右侧的 `2×` `4×` 被挤出屏幕，点不到。

**定位**：工具按钮那一行是 `display:flex` + 按钮 `white-space:nowrap`，
且中间有个 `<div style="flex:1 1 auto">` 占位把右侧推到屏幕外，
容器没有 `overflow`，超出的部分既不能滚也点不到。

**修法**：

- 工具行加 `.row.scroll`：`flex-wrap:nowrap; overflow-x:auto`，窄屏可横滑
- 按钮加 `flex:0 0 auto`，不被压扁
- `≤640px` 时把倍速组单独换行，永远点得到
- 去掉那个 `flex:1 1 auto` 的占位宽度（改成 `min-width:8px`）
