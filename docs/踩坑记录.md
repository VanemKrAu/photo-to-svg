## 1. `--order sketch` 的「线稿」根本不是线稿

**现象**：用户看回放说「这画得乱七八糟的，还不是先画的线稿」。

**定位**：`build_svg_art.py` 的 `order_shapes()` 里，所谓线稿的筛选条件是

```python
thin_cap = max(24.0, total_px * 0.0002)      # ≈622 px²
if area > thin_cap: continue                 # 只筛「面积够小」
if perimeter / (2*sqrt(pi*area)) >= 2.0: ...  # 只筛「形状够细长」
head = lines[: int(len(shapes) * 0.02)]      # 再按周长降序取前 2%
```

实测被选中的前 2163 笔：**bbox 中位数 31×21**，bbox 覆盖率 **61.9%**。
也就是说它们是**全图颜色过渡处的细长碎片**（天空色带、海浪纹、沙滩颗粒），
散布在整幅画面上，跟人类画线稿（沿物体轮廓、首尾相连）完全不是一回事。

**修法**：不要指望 `--order` 给线稿。真正的线稿层由 `svg2canvas.py` 的
`build_lineart()` 从原图单独提取（见 #5），插在所有色块最前面。

## 2. 纯 SVG 版有「白点」

**现象**：用户反馈「svg 图片里面有白色的部分好像是没画到一样，零零散散的白点」。

**定位**：`write_svg()` 写出的 `<path>` **只有 fill、没有 stroke**，而 `write_html()` 写出的
自带 `stroke="{同fill}"` + CSS `stroke-width`。色块是互不重叠的平面划分，轮廓简化
（epsilon）会让相邻色块之间留下发丝级细缝；HTML 版靠同色描边把缝糊住，纯 SVG 版没有描边
→ 缝里露出底层 `<rect fill="#f0f0f0">` 的浅灰底，在深色区域就是刺眼的白点。

**修法**（`make_art.py` 已自动做）：

```python
t = re.sub(r'<path fill="([^"]+)" fill-rule="evenodd"',
           r'<path fill="\1" stroke="\1" fill-rule="evenodd"', t)
t = t.replace('</title>', '</title>\n<style>path{stroke-width:0.6;stroke-linejoin:round}</style>')
```

1440×2162 原生分辨率实测：亮斑 7091 → 379 个（−95%），MAE 4.93 → 4.04。

## 3. stroke-width 越大越糊

**现象**：修完白点后用户说「这样感觉非常糊，能不能更清晰一点」。

**定位**：同色描边会把每个色块**向外撑 stroke/2**。图里有 4.8 万个只有 2~4px 的小色块，
被撑大之后直接被隔壁颜色吃掉，细节就没了。

1440 原生分辨率实测（对照原图算 SSIM）：

| 配置 | SSIM@1440 | MAE | 白点 |
|---|---|---|---|
| 顶配 67990 笔 + **sw 1.8** | **0.8642** | 4.39 | 1076 |
| 顶配 67990 笔 + 无 stroke | 0.8864 | 3.85 | 14578 |
| 顶配 67990 笔 + sw 0.6 | 0.9126 | 3.49 | 812 |
| 超高精度 182640 笔 无 stroke | **0.9434** | 2.24 | 687 |

**结论**：① 描边最优区间 **0.3~0.6**，1.8 反而最糊；② **想更清晰，加形状数远比加描边有效**；
③ 算 SSIM 缩放必须统一用 `cv2.INTER_AREA`，用 LANCZOS 会得出相反结论。

## 4. 「线稿画着画着突然大面积上色」

**现象**：用户反馈线稿阶段结束后画面「啪」地糊上一大片。

**两个原因叠加**：

1. 速度曲线突变——原来线稿阶段每笔耗时是后面的 27 倍，过点后速度猛提。
2. **笔的粒度断崖**（主因）——色块按面积降序排，实测

   > **整幅画面 75% 的面积，是在前 1.94% 的笔里铺完的。**

   线稿 2621 笔之后，紧接着的第 88 笔就盖掉了半个画面。

**修法**：

- **时间权重 = `0.15 + bbox面积 × 0.002`**（大色块慢慢铺、小碎片快过）。
  线稿层默认按「√bbox面积（≈线长）」估重、不单独占时间（实测占 3~4%）；
  只有显式指定「线稿时间占比」时才把线稿反解成固定比例 —— 固定 15% 会把
  起稿拖到十几秒，2026-09-12 起默认不再用。
  面积数组作为 `Uint32×N` 追加在 payload 末尾，JS 用累计权重表 + 二分查找做
  「时间 ↔ 笔序号」双向映射。**别用分段线性曲线**。
- **大色块扫描线切分**：bbox 面积 > 7000 的色块，用 `cv2.fillPoly` 光栅化后按横条切开
  （step = 9000/宽度，夹在 [8, h]），像大笔刷一横条一横条刷上去。

改后覆盖曲线（90 秒；当时线稿还按固定占比走，现已改为默认自然分配）：

| 时间 | 15%(线稿毕) | 25% | 35% | 45% | 55% |
|---|---|---|---|---|---|
| 画面已铺 | 11% | 32% | 60% | 87% | 96% |

## 5. 线稿做成了「几何色块」

**现象**：用户看走廊人像的回放，说「你这也不是线稿啊全是几何形状」。

**定位**：`build_lineart()` 一开始用的是

```
Canny → dilate 膨胀 → findContours 取外轮廓 → 用多边形 fill
```

边缘一到密集区域（棕榈叶、百叶窗、木纹、栏杆立柱），膨胀后会连成一整片，
轮廓简化成一个多边形，**一填充就是一坨灰色三角形**。

**修法**：不再膨胀、不再填充。改成「**折线追踪 + 描边**」：

1. Canny 得到 1px 边缘，把边缘像素放进 `set`
2. 按 8 邻域走链，优先从度=1 的端点起步（保证一条线尽量完整），剩下的闭环再任意起头
3. `approxPolyDP(1.0, closed=False)` 简化，按 `seg_pts=16` 点切段
4. **用 `ctx.stroke()` 画**（`lineCap/lineJoin=round`，线宽默认 2.6 画布像素）

类型标记：颜色值的 `0x02000000` 位表示「这一笔是描边，不填充」。

**效果对比**（走廊人像 1440×2012）：

| | 填充式（错） | 折线描边式 |
|---|---|---|
| 线稿落在真实边缘上 | 64.7% | **97.8%** |
| 墨水占画面 | 11.18% | 6.52% |

## 6. 线稿整体错位 / 看着像「另一张图的线稿」

**现象**：用户说「你最开始给我弄那个线稿图，预览是上一次海边人像的那个线稿图」。

**定位**：`svg2canvas.py` 里把画布尺寸**硬编码成了 1440×2162**（海边那张的尺寸）。
但走廊人像是 **1440×2012**。于是：

```
原图 1440×2012 → 被拉伸成 1440×2162（高 7.5%）→ Canny 提边缘（坐标是 2162 高的）
             → 画到 1440×2012 的画布上 → 超出部分被裁掉
```

两头都错：线条纵向滑位（越靠底部错得越多，底部差 150px），底部还有一整段被裁。
同时页面里 `<canvas height="2162">` 也和实际画面不符，显示时被再拉一次。

**修法**：画布尺寸**一律从 SVG 的 `viewBox` 读**：

```python
mv = re.search(r'viewBox="0 0 ([\d.]+) ([\d.]+)"', head)
CW, CH = int(float(mv.group(1))), int(float(mv.group(2)))
```

修完「线稿落在真实边缘上」21.6% → 64.7%（后经 #5 再提到 97.8%）。
`make_art.py` 已加「SVG viewBox / 页面 canvas」三方尺寸自检，不一致直接报错退出。

> 自检本身也要**流式扫描**：回放页 `--ghostimg` 的原图 base64 有两三百 KB，
> `read(N)` 读不到后面的 `<canvas>`。

## 7. 出现很多横向白线

**现象**：用户说「出现了很多白线，上一次还没有」。

**定位**：新加的扫描线切分（#4）里，相邻横条的像素范围不重叠：

```
条0 覆盖到第 134 行
条1 从    第 135 行开始     ← 中间缺一行，露出底色 #f0f0f0
```

**修法**：让每条多含一行 —— `mask[yy : yy+step+1]`，相邻条共享同一行像素。

修复后逐行扫描（找「近白像素占比突然飙升」的行）：成片 → **只剩 3 行**
（其中 2 行在地平线位置，那里原图本身就是亮的）。

## 8. 手机打开非常卡

**现象**：用户说「我现在手机已经非常卡了，这个十几兆的 HTML 文件我打开就很卡了，不能优化一下吗？两者必须取舍是吧？」

**定位**：`write_html()` 把 N 个 `<path>` **全部塞进 DOM**，每个还挂一条 CSS 动画。
67990 笔时手机就卡，18 万笔根本打不开。

**修法**：改用 Canvas（`svg2canvas.py`）：

- DOM 里只剩 **1 个 `<canvas>`**，笔数据打包成二进制 base64 内嵌
- **逐帧增量绘制**（只画新增的几十笔），拖动回退时才整幅重画
- 拖动节流到 `requestAnimationFrame`
- 解码用 `new Uint8Array(L)` + for 循环，**别用 `Uint8Array.from(atob(s), …)`**
  （12 MB 会生成 900 万元素的中间数组）

| | 旧 HTML | 新 Canvas |
|---|---|---|
| 笔数 | 67990 | **182640** |
| 文件 | 20.9 MB | **12.4 MB** |
| DOM | 67990 path + 67990 动画 | **1 canvas** |
| SSIM@1440 | 0.9126 | **0.9406** |

**所以「清晰」和「流畅」不必取舍——瓶颈是渲染方式，不是数据量。**

## 9. 解析 path 的正则被属性顺序坑了

**现象**：`make_art.py` 首次端到端自检时，`svg2canvas.py` 解析出 **0 个色块**。

**定位**：`make_art.py` 的「补描边」步骤会在 `fill` 和 `fill-rule` 之间插入 `stroke`，
而 `svg2canvas.py` 的正则写死了属性顺序：

```python
re.compile(r'fill="([^"]+)" fill-rule="evenodd" d="([^"]*)"')   # ✗ 匹配不到
```

**修法**：放宽成不依赖顺序：

```python
re.compile(r'fill="([^"]+)"[^>]*?d="([^"]*)"')                   # ✓
```

## 10. 命令行参数错位

**现象**：生成出来的线宽是 `0.25`（本意是 2.6），线细到看不见。

**定位**：`svg2canvas.py` 的位置参数是

```
<in.svg> <原图> <out.html> <标题> <秒数> <线稿笔占比(0=自动)> <线稿时间占比> [线稿线宽]
```

调用时把 `epsilon` 传到了第 8 位（线宽的位置）。

**教训**：参数一多就容易错位。`make_art.py` 是唯一入口，它的参数顺序固定为
`<原图> <作品名> [标题] [秒数] [线稿时间占比] [epsilon] [线宽]`，改调用时**数一遍位数**。

## 11. 越还原越好，但 epsilon 可以「白捡」

**现象**：需要在「保真」和「体积」之间取舍。

**定位**：`epsilon` 是轮廓简化容差，它**只影响顶点数，不影响形状数**：

```
epsilon 0.08 → 形状 182640，顶点 2951257，SSIM 0.9434
epsilon 0.25 → 形状 182640，顶点 1490435，SSIM 0.9406      ← 顶点少一半，SSIM 只差 0.003
```

**结论**：给 Canvas 回放页（要发到手机上）时用 0.25，文件从 20.5 MB 降到 12.4 MB；
要极致保真的矢量原图时用 0.08。

## 12. 其它零碎

- **底板恒为纸白 `#f0f0f0`**（`make_art.py` / `web_run.py` 里的 `PAPER`，两处必须同值）。
  源码里「与底板色差 ≤3 的量化色」会**整簇跳过不画** —— 底板同时决定显示与跳过判定，
  所以 SVG 底板 rect 与回放页 canvas 背景都从它取，永远同源（见第 20 条）。
- **`--dark-cut` 恒给 0**：给正值会把与底板相近的暗部整片压平（皮肤阴影、水渍、暗部渐变），
  实测能压平 26% 的画面，用户反馈「治标不治本」。
- **`--base`** 按 `60 ÷ 笔数` 估算，让 1× 播放落在 60 秒左右；忘了给会变成几十分钟。
- **千万不要用「读图片」工具读 png/jpg**，改用 Python 分析像素（见 AGENTS.md 规则 1）。
- **不要往工作区根目录扔文件**——用户为此发过火，产物一律进 `output/<作品名>/`。
- **不要生成用户没要求的文件**。曾自作主张放了一张「线稿层预览.png」，
  用户说「你怎么也给我弄了个线稿图预览，而且预览图还不对」。

## 13. 底色选错 → 满图白点

**现象**：网页版生成的一张海边照，画面边缘和阴影处出现成片白点。
用户对比原图后指出「为什么又出现白点了」。

**定位**：`pick_background()` 在最高频色占比 ≥5% 时就拿它当底色，
而底色的作用是「哪些颜色可以整簇跳过不画」（源码里 `|rgb - matte| ≤ 3` 就跳过）。
那张照片的最高频色是 `#686868`，占 **5.94%**，刚好越过阈值 ——
而 `#686868` 正是画面里的**阴影灰**。于是人物和沙滩上的阴影被整簇挖掉，
底下 `#f0f0f0` 的底板从缺口透出来，就是白点。

**修法**：阈值从 5% 提到 **12%**，且只在明确是「统一背景」时才用高频色；
其余一律用画面里不存在的中性色（`#f0f0f0` / `#101010`，按画面明暗挑）。

| | 旧阈值 5% | 新阈值 12% |
|---|---|---|
| 那张海边照 | 误用 `#686868` → 挖空阴影 | 用 `#f0f0f0` → 安全 |
| 色块数 | 52,467 | **52,988**（多画出 521 块被挖掉的内容） |
| 孤立亮点 | 成片 | **0.0001%** |

代价是底色与画面不同时，SVG 体积略增（底板色差大时压缩率差一点），
但换来「绝不会挖空画面」——这笔账很划算。

**排查提示**：如果以后再见到白点，先看 `pick_background` 选了什么色，
再用 `|rgb - matte| ≤ 3` 去原图里数一遍有多少像素会被跳过。

## 14. 回放页工具栏在窄屏溢出，倍速按钮点不到

**现象**：手机上打开回放页，底部工具栏右侧的 `2×` `4×` 被挤出屏幕，点不到。

**定位**：工具按钮那一行是 `display:flex` + 按钮 `white-space:nowrap`，
且中间有个 `<div style="flex:1 1 auto">` 占位把右侧推到屏幕外，
容器没有 `overflow`，超出的部分既不能滚也点不到。

**修法**：

- 工具行加 `.row.scroll`：`flex-wrap:nowrap; overflow-x:auto`，窄屏可横滑
- 按钮加 `flex:0 0 auto`，不被压扁
- `≤640px` 时把倍速组单独换行，永远点得到
- 去掉那个 `flex:1 1 auto` 的占位宽度（改成 `min-width:8px`）

## 15. 宽屏两栏：左栏卡片越界压到右栏，右栏剩半屏空白

**现象**：PC 上打开网页版，左栏卡片比右栏宽出一截、两栏贴在一起，
右栏除了一张矮卡片全是大片空白（1280 视口下量到 533px），
「开始生成」按钮被拉成 780px 宽的横条。

**定位**：两个独立问题叠在一起。

1. **卡片越界**：`.card` 是 grid 子项，默认 `min-width:auto`，压不到比内容最小宽度更窄；
   而参数卡的 `.seg` 是 `repeat(4,1fr)`（1fr 的下限同样是内容宽度），
   按钮里的 `<small>` 又写了 `white-space:nowrap`。四个按钮的最小宽度加起来 412px，
   加上卡片内边距 = **454px > 列宽 400px** —— 卡片直接撑破列，压到右栏上（实测重叠 36px）。

2. **右栏空白**：右栏只有一张「生成」卡（119px 高），但两栏被 stretch 拉到同高（652px），
   多出来的 533px 没有内容。

**修法**：

- `.card{min-width:0}` + `.seg{grid-template-columns:repeat(4,minmax(0,1fr))}`，
  让卡片和按钮都能真正收缩（`small` 本来就有 ellipsis 兜底）
- 重新分栏：**左栏 = 控制面板**（选图 → 参数 → 生成，固定 480px），
  **右栏 = 输出**（结果 → 历史）。生成按钮回到 418px 的正常宽度
- 结果卡在宽屏**常显**：没结果时是一块空状态引导区（虚线框 + 三步提示）并 `flex:1` 撑满右栏；
  手机上仍是「生成前不显示」，避免页面底部多一块空卡片

**验证**：1060 / 1280 / 1440 / 1920 四档视口下量过 —— 无重叠、无横向溢出、按钮文字无截断，
左右栏高度 792 = 792 完全对齐。

**经验**：分栏布局里，凡是「多列 grid + nowrap 文字」的组合都要显式压住 `min-width`，
否则内容会先撑破自己的卡片、再压到隔壁栏上，而且往往在小视口才暴露。

## 16. 回放页「放大了还用不上全屏」+ 缩放条压住画面

**现象**（手机用户报的）：
① 全屏后缩放工具条浮在画面右下角，正好压住图；
② 图片放大后仍然只在那条「小框」里，上下全是黑边，用不上整屏 ——
用户原话：「不应该是像正常图片一样放大显示的范围是整个手机屏幕吗？」

**定位**：`.frame` 当初是照「贴合图片的小框」设计的 ——
`height:100%; aspect-ratio:W/H`，JS 再把它设成 `min(视口宽/W, 视口高/H)` 算出的尺寸。
于是：

- 它天生比可用区域小（横图在竖屏上只占 1/3 高，其余是黑边）；
- 放大走的是「画布的 CSS `transform`」，超出的部分被 `.frame` 的 `overflow:hidden`
  裁掉 —— 所以「放大」只是在小框里放大，周围的屏幕空间永远用不上；
- `.zoombar` 又是 `.frame` 内的 `position:absolute`，必然跟着框压在图上。

**修法**（把「图片框」改成「视口」，也就是相册模型）：

- `.frame` 改为撑满可用区域（`flex:1 1 auto; align-self:stretch`），去掉 `aspect-ratio`；
  新增 `.view` 画面容器（canvas 和对照层都放里面），尺寸 = 适配尺寸，
  统一套「居中 + 缩放 + 平移」的 transform
- `applyView` / `clampPan` / `setZoomAt` 全部改成按**视口尺寸**算
  （原来按画布原始像素算，平移范围差了一个 `fitScale`，放大后能拖出黑边）
- `.zoombar`（毛玻璃浮框）从 `.frame` 挪到 `.stage`：定位基准从「画面」换成
  「整个观感区域」，于是它钉在画面区右下角（紧挨底部工具栏上方），不再跟着图片走。
  中途试过把它并进 `footer` 做成一行，用户否了 —— 原话「要之前那种框（毛玻璃），
  把那个工具框放到界面右下角就行，不是直接让你和最下面的工具栏融为一个」
- 双击从「切全屏」改回「1× ⇄ 2.5×」（全屏只保留按钮 / F 键，双击缩放更符合相册习惯）

**验证**（iPhone 13 模拟 + 各视口）：初始 100% 宽撑满；放大 196% 后图片覆盖视口
**100% × 100%**；拖到极限露边全为负（图片始终盖住视口，不会拖出黑边）；
`footer` 行序 = 进度条 → 缩放条 → 按钮栏；390 / 844 / 1280 / 1600 四档视口均正常。

**经验**：凡是「能放大」的看图界面，承载缩放的容器必须是**视口**（撑满可用区域），
而不是**贴合内容的框** —— 否则放大就只是在小框里裁剪，永远用不上整屏。

## 17. make_art.py 里两份 pick_background：命令行入口静默坏掉

**现象**：`make_art.py` 一运行就报 `ValueError: too many values to unpack (expected 3)`。
`py_compile`／`ast.parse` 这类语法检查**完全发现不了**——文件语法合法，
两份同名函数在运行期互相覆盖。

**定位**：文件里存在两份 `pick_background()`：头部一份新版（12% 阈值、返回 3 个值），
中部还留着一份旧版（5% 阈值、返回 4 个值）。**Python 后定义者胜**，实际生效的是旧版；
而 `main()` 是按新版写的（`bg, dark_cut, ratio = ...` 解包 3 个）→ 一跑就崩。

源头是「修白点」那次提交：新版函数被插到了文件**头部**而不是替换原函数，旧版没删。
之后命令行入口一直是坏的——网页版走 `web_run.py`（自己带一份函数、不受影响），
所以这个问题一直没有暴露出来。

**修法**：删掉头部重复段、用新版替换中部的旧版（阈值与 `web_run.py` 语义一致）。
修完 240 行、单一定义，实跑通过。

**防线（本次一并加上）**：`smoke_test.py` 的语法检查升级为「语法 + 顶层重复定义」双查：
用 `ast` 遍历顶层 `def`/`class`，重名就报错并列出各自行号。

**教训**：语法检查只能保证「能编译」，保证不了「跑起来对」。
大段编辑之后**实跑一次**，比任何静态检查都可靠。

## 18. 历史回放页的升级规则：all-or-nothing 在多世代数据上等于「永远不升级」

**现象**：用户报「改完之后，网站上还是有那三个问题」，另外还提到「右侧原图不能滚动（缩放）」。
可代码确实是最新的 —— 模板端检查全过，用真实鼠标事件复测**新生成**的回放页，
四个现象全部消失。那问题就在别处。

**定位**：不在模板，在 `web/index.html` 里给**历史记录**做的升级（`LAYOUT_RULES` / `upgradeLayout`）。
它要求**全部规则命中才应用**，任何一条对不上就整体放弃。
而规则是按世代累积的（第 0 条针对最早那批、最后几条针对最新那批），用户的历史记录横跨好几个世代。
实测 `0a7cbbc` / `83dbe13` / `ea3acd6` 三个世代的产物**全部卡在第 0 条**：

    规则 #0 [re] /  \/\* 首帧兜底尺寸[\s\S]{0,400}?touch-action:none\}/
    → re 不匹配 → upgradeLayout 返回 null → 页面保持旧样

第 0 条是给最早期页面用的（要求含「首帧兜底尺寸」那段注释），中期页面早就没有它了，
于是后面 30 条（`#sideView`、指针捕获、双栏隐藏对照层）**一条都轮不到**。
用户看到的双栏叠半张原图、分界线跟鼠标、拖拽粘住、右栏不能滚轮缩放，
全都是这批「升不上去的老页面」的表现。

**修法**（`upgradeLayout` 改成逐条独立 + 幂等判定）：

- 每条规则自己判定：命中就替换、命中不了就跳过（顺序保留，后面的规则依赖前面的输出）；
- 但**逐条独立必须配「这条是不是已经打过了」的判断**，否则会重复打补丁 ——
  有些规则的 `from` 并不唯一标识旧状态。实测对最新产物误命中 4 条，
  最狠的是 `from: '</footer>'` 那条：会给已经补过按钮的页面**再插一个 `#fsExit`**，
  `var fitW` 声明也会被插两遍；
- 判定方式：取 `to` 里**相对 `from` 新增的代码行**，按连续段切块，**每块都命中**才算打过。

**修这个判定时踩的三个连环坑**（前两个的后果都是「该升级的升不上」，第三个是「不该升的被反复升」）：

1. 拿「最长的一行」当哨兵 → `ghostEl.style.display=ghostOn?"block":"none";` 在文档别处也有
   （「对照」按钮的点击处理里就是这两行），把没打过的页面误判成打过了，
   「双栏隐藏对照层」于是永远加不上；
2. 排除注释行时用了 `t.endsWith('*/')` → 把**行尾挂注释的代码行**
   （`var fitW=0, fitH=0;  /* … */`）也当注释排掉，这条规则又认不出自己打过了；
3. 构建哨兵块时对行做了 `trim()`，却拿它去匹配**带缩进的原文** → 永远匹配不上，
   「已经打过」恒为 false，同一条规则被反复应用。`upgradeLayout` 的**幂等断言**把这条直接抓了出来：
   `upgrade(upgrade(x)) === null` 不过，就说明有规则在重复命中。

**另有一处规则本身缺的**：「双栏隐藏对照层」这段代码只存在于**老布局那条规则**的 `to` 里，
而它的 `from` 要求 `var cell=(aw-GAP)/2` —— 中期页面匹配不到，
也就是说这批页面**没有任何规则**能拿到这个修复。补了一条
「相册式布局已就位、但还早于该修复」的规则专门覆盖它们。

**教训**：处理「历史数据升级」时，`all-or-nothing` 看着安全（不会半新半旧），
但只要**数据的版本跨度大于规则的跨度**，它就退化成「永远不升级」，而且是**静默失败** ——
代码看着对、日志没有错，只是没有任何一条记录真的被升级。规则该按世代分组或逐条独立，
并且**每条都要能判断自己是否已经应用过**。
还有一条验证纪律：**一定要跑「升级后的产物」**，只测新生成的页面会得出「已经修好了」的错误结论。

## 19. 双栏从「共享视角」反过来改成「各自独立」：在升级规则里带出一个连锁坑

**来由**：用户要求双栏下滚轮 / 拖动只作用于鼠标所在的那一栏 —— 悬停右栏滚轮只该缩原图、
拖原图要能拖动、拖左栏时原图不该跟着跑。
上一版（4407b45）的设计恰好**相反**：「`#sideView` 与左栏共享同一套缩放/平移，两边永远看同一区域」，
而且右栏压根没绑拖动（所以「拖原图拖不动」）。这次不是修 bug，是**把设计反过来**。

**改法**：右栏拆出自己的一套 `zoom2`（s/tx/ty）与 `applySide` / `clampPan2` / `setZoomAt2` / `resetSide`，
滚轮与指针事件只绑 `#side`；左栏 `applyView` 不再同步右栏；新增 `lastPane` 记住最后操作的是哪一栏，
底部 `±` 与键盘 `+/-` 作用于它，`⤢` / `1:1` 仍是全局动作两栏一起归位；
`#side` 补 `touch-action:none`（否则触屏单指拖动会被浏览器当滚动手势吃掉）。

**升级规则那一步带出个连锁坑**（这次最值得记的）：

- 老页面要过**两段**升级：先被既有规则升到「共享版」，再被新加的 9 条规则改成「独立版」；
- 既有规则里有一条（「给左栏 wheel 后面补上共享版的右栏滚轮监听」）的 `from` **只是左栏那三行**。
  独立版页面里这三行还在，于是它照样命中，把一段**共享版**监听又插回去；
  紧接着新加的那条再把它改成独立版 —— **净结果看着是对的**，所以浏览器里的功能测试全过，
  但每跑一次都会改写一遍：幂等断言（`upgrade(upgrade(x)) === null`）直接把它抓了出来。
  顺序稍有不同就会**两段监听同时存在**，右栏滚一次缩放到 1.18² 倍。
- 修法：给那条规则加显式 `sentinel`，用**共享版和独立版都有**的特征串
  （`sideEl.addEventListener("wheel", function(e){`）判断「已经补过了」。
  第 18 条那套通用启发式在这里不够用 —— 它按 `to` 的新增代码行判断，
  而两版新增的代码**完全不同**，认不出来。

**教训**：给历史数据写升级规则时，**新规则会和旧规则作用在同一段代码上**，
必须把「升级后的结果再跑一遍」当成硬性断言（幂等）—— 只看最终功能对不对会漏掉这类问题。
另外，`from` 覆盖的文本范围越窄越危险：它可能在一个**已经升级过**的页面里依然匹配，
从而把旧的实现又插回去。

## 20. 底板固定纸白 + 取消「整簇跳过」

**来由**：用户先后提了两件事 —— ①「让 SVG 绘图时背景也是白的，有在纸上画图的感觉，
不要自动取色背景」，并明确**不要直接回滚**上一次那笔底板改动；②「每个地方都必须画出来，
不要跳过」。

### ① 底板固定纸白

**为什么不能只把回放页刷白**：底板身兼两职 —— 它既是要显示的底色，又是「哪些色块可以
整簇跳过不画」的判定基准（源码里调色板色与底板色差 ≤3 就整簇略过，见下一节）。
只把回放页刷成白色、而 SVG 底板仍是深色，被跳过的深色区就会露出白底，
**正好复现第 13 条那个白点 bug**。所以干净的做法是**统一源头**：底板恒为纸白，两边天然同源。

### ② 取消整簇跳过

`build_svg_art.py` 的 `trace()` 里原本有这样一道省笔优化：

    if int(np.abs(rgb.astype(np.int16) - matte).max()) <= 3:
        continue          # 与底色同色：不必画

它在**调色板颜色**这一层整簇跳过。可填充色取的是**区域真实均值**、并不是调色板色本身，
于是被跳过的块露出的底板色和该处真实颜色并不一致 —— 浅色图上就是一块块「没画到」的方斑。
用户要求全部画出来，这段直接删掉（`background` 参数保留在签名里，底板 rect 仍由
`write_svg` 写，调用方接口不变）。

**改法**：

| 位置 | 改动 |
|---|---|
| `tools/make_art.py` | `pick_background()` 恒返回 `PAPER = "#f0f0f0"`，不再判高频色/明暗 |
| `web/web_run.py` | 同一份逻辑同步改（网页版不走 `make_art`，两处必须一起，见第 17 条） |
| `tools/build_svg_art.py` | `trace()` 删掉「与底板色差 ≤3 整簇跳过」；`--background` 默认 `#000006` → `#f0f0f0` |
| `tools/verify_svg.py` | `--bg` 默认 `#000006` → `#f0f0f0`（否则比对的是另一份结果） |
| `skill/extras/*` | 同名脚本 `cp` 同步（`smoke_test.py` 会查分叉） |

`svg2canvas.py` 一行没动 —— `b236f14` 那次「回放页从 SVG 读底板」的机制现在依然必要。

**实测**（都跑完整流程，同一张图前后各一遍）：

| 测试图 | 有跳过 | 无跳过 |
|---|---|---|
| 浅色图（白底占 83%） | 9,378 块 / 1.1 MB | **12,600 块 / 1.6 MB（+34%）** |
| 深色走廊人像（512²） | 37,758 块 | 37,758 块（**无变化**） |
| 深色图 · 改纸白之前（底色 `#080808`） | 31,565 块 | — |

两句话总结：跳过只对「接近底板的颜色」生效 —— 浅色/白底图因此白省掉三分之一以上的笔数，
深色图几乎不受影响；而改纸白本身让深色图多画约 20%（暗部不再融进深色底板）。
深色图以纸白起笔、逐笔把暗部画上去，正是「在纸上作画」的观感。

**注意**：历史作品的底板不会自动变白 —— 升级规则按 **SVG 里的底板色**修正回放页，
而老 SVG 的底板仍是旧值，要重新生成才是白底。

## 21. 线稿「亮度过滤」误杀长轮廓：亮背景图几乎没线稿

**现象**：用户报「线稿在物体边缘都没描完就开始画其他部分」——回放里起稿阶段只剩零散碎线，
物体轮廓大面积缺失。

**定位**（用 4 张原图复现，统计在长边 1600px 的预览尺寸上做）：问题出在第 2 版判据
「链的平均亮度 ≤110」—— 它只看「线画在亮区还是暗区」，而**亮背景照片**（白墙、天空、
亮肤色）里的真轮廓平均亮度同样高，全被一刀切掉：

| 作品 | 被删的链 | 其中「长 ≥30 且边缘强度 ≥120」 | 最长被删链 |
|---|---|---|---|
| 走廊人像 | 638 条 | 223 条 | **1022 px** |
| 银发背影 | 652 条 | 229 条 | 370 px |
| 海边人像 | 1002 条 | 273 条 | 230 px |

一条连续 1022 像素的链不可能是照片纹理，只可能是地面/墙体的交界线。
（对比：这些被删链的边缘强度与保留下来的链相当，"弱边缘"的说法站不住。）

**修法**（`build_lineart()`）：加「**长链豁免**」——追出来的链只要 **≥24 点就一律保留**
（照片纹理不可能有连续 24px 的成形边缘），短链继续按「平均亮度 ≤110」压纹理，
保住上一轮「脸上不长黑斑」的修复。

**实测**（同一张图、全尺寸、只改这一条判据）：

| 作品 | 旧判据 | 新判据 | 增幅 |
|---|---|---|---|
| 走廊人像 | 624 笔 | **1,052 笔** | +69% |
| 银发背影 | 109 笔 | **598 笔** | +449% |
| 海边人像 | 957 笔 | **1,555 笔** | +62% |
| 夜景人像 | 44 笔 | **62 笔** | +41% |

**回归验证**：同一份回放页 seek 到 100%，新旧两版最终画面的像素差 **0.056%**
（差异只落在色块缝隙处的线稿边缘）—— 色块层零影响；被找回的线稿只在「起稿阶段」可见
（之后被色块盖住），正是用户反馈的场景。

**注意**：线稿是生成时算的，已有作品需重新生成才有新规则。

## 22. 升级层改造：从「模糊规则」到「版本戳 + 迁移链」+ 黄金样本测试

**来由**：网页版的历史升级层（把用户浏览器里存的旧回放页升到新样子）攒到了
**42 条规则、656 行**，占 `web/index.html` 近四分之一。它的结构性问题在两年前后
（#18 / #19）暴露过：规则的 `from` 是「文本指纹猜世代」，每次改回放页模板都要把
「新老代码对照」手工追加成新规则 —— 只能累积、无法收敛，还修过两个**静默失败**。

**改法**（一次结构性替换，外加一套测试基建）：

1. **生成端打版本戳**：`tools/svg2canvas.py` 的模板在 `<title>` 前生成
   `<!-- p2sv-gen: v1 -->`；改模板行为时版本号 +1。
2. **升级端走精确迁移链**（新文件 `web/upgrade.js`，纯函数库）：
   - 有戳 → `MIGRATIONS` 逐级 `{ from, to, apply }`，应用一条、版本推进一级；
     **幂等性由版本号保证** —— 迁移完版本号已变，再跑对不上 from，
     「这条打过了吗」的启发式判定（#18 第三个连环坑的根源）从结构上消失；
   - 无戳存量 → 照旧跑 42 条模糊规则（**冰冻遗产**，不再新增），
     升完补戳为 `LEGACY_TARGET（=1，恒不变）`，再接上迁移链；
   - 迁移约定：`apply` 返回 null = 未命中（跳过但推进版本，不卡死）、
     抛异常 = 捕获记录照样推进、缺环才停下并记 note。
3. **黄金样本测试**（`tools/test_upgrade.js`，node）：
   `tests/fixtures/` 里是**七个世代的真实产物**（`tools/make_upgrade_fixtures.py`
   从 git 历史逐个 checkout 当年的 `svg2canvas.py` 重新跑出来；管线确定性，
   重生成**字节级一致**）。断言：版本戳 / 幂等（升级结果去戳再升 == 从原件升）/

   （PAPER 6 处 / 默认参数 / 模板戳 = GEN_LATEST，防「改一处忘一处」）。

**过程中发现的两个事实**（都不是 bug，写进了 `docs/历史升级机制.md`「已知边界」）：

- **最老世代（初版 29770ea）升级后没有完整缩放系统**：那代页面里根本没有缩放，
  文本替换补不出整套函数 —— 页面能播能看、零报错（**安全降级**）。网页版 9-12
  才上线，用户历史里不可能有这代产物；样本只用于压测最坏情况，测试对它断言
  「结构升级 + 不破坏」，不断言全套交互。
- **模糊规则对中间世代是「能升多少升多少」**（#18 的逐条独立设计使然）：
  个别规则可能对某些世代不命中。测试断言按**性质**写（该拿到的升级拿到），
  不按「全等于最新模板」写。

**教训**：给「历史数据」写迁移，**版本号是结构性的解** —— 把「猜」变成「读」，
把「无限累积的规则」变成「每代一条、写完冻结的迁移」。再配一套**真实世代样本**的
测试（#18 的教训说「一定要跑升级后的产物」，这次把这句话落成了 93 项断言），
这类静默失败才会在提交前浮出来，而不是等用户报「改完了怎么还有问题」。
